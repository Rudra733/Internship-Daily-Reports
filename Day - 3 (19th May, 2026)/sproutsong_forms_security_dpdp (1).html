ℹ Medium-risk form. Collects school-level institutional PII and contact person data. No student data. Primary purpose: scheduling product demonstrations for schools. URL: https://auth.sproutsong.com/request-demo
What data do we collect?
School identity: schoolName, trustName (optional), schoolEmail, schoolPhone, schoolLogo (URL).

Contact person: contactPerson (name), contactEmail, contactDesignation, primaryContact (phone), altMobile (optional).

School profile: state, city, type (Primary/Secondary/Higher Secondary/K-12), board (CBSE/ICSE/SSC/IB/Cambridge/Other), medium, numberOfStudents, pedagogyType.

Demo preferences: preferredDate, preferredTime, demoPreference, followUpMode, notes (free text).

Server metadata: status, adminStatus, scheduledAt, submittedAt, consentGiven, consentTimestamp, consentIP.
Why do we collect it?
School identity & profile → To identify the school, assess fit for SproutSong's product, and personalise the demo content to the school's board, medium, and pedagogy.

Contact person details → To reach the right decision-maker at the school and schedule the demo session via their preferred contact channel.

Demo preferences → To match available slots, confirm the appointment, and follow up appropriately. Notes allow the school to communicate specific needs.

Metadata (status, adminStatus) → Internal CRM-style tracking for SproutSong's sales/demo team to manage the pipeline from "New" to "Demo Done".

No data is collected for advertising, profiling, or third-party sharing.
Where is it stored?
Primary store: MongoDB — demoRequests collection. All form fields are stored here as a single document per submission.

PII fields at rest: schoolEmail, schoolPhone, contactPerson, contactEmail, primaryContact, altMobile are encrypted using field-level encryption (mongoose-field-encryption or MongoDB CSFLE) with a 32-byte key stored in environment variables — never in the codebase.

schoolLogo: If a URL string, stored as-is (validated format only). If file upload is added in future, files must go to a private cloud bucket (AWS S3 / GCS), never a public /uploads folder.

No data is stored in browser localStorage, cookies, or third-party analytics tools. Server logs must mask email and phone fields before writing to any log stream (CloudWatch, Papertrail, etc.).
Who can access it?
SproutSong demo/sales team → Read + update access to assigned records (adminStatus, scheduledAt, notes). Cannot delete records without super admin approval.

SproutSong super admin → Full CRUD access. Can export, bulk update status, and process deletion requests.

School contact person (submitter) → No portal access. They receive an email confirmation only. They can request data deletion via privacy@sproutsong.com.

No access for: other schools, students, parents, third-party vendors, or advertising platforms.

Access enforcement: All access must go through the authenticated API with JWT-based role checks. No direct MongoDB access for any team member in production. Admin panel routes must require role: "admin" or role: "sales" middleware.
How long do we keep it?
Submitted & active records → Retained for 12 months after the last interaction (last status change or scheduled demo date), then auto-deleted.

Draft records (status = "draft", never fully submitted) → Auto-deleted after 30 days via MongoDB TTL index on createdAt.

Closed / rejected records (status = "Closed") → Retained for 6 months for audit trail, then purged.

On deletion request: Hard-delete the document within 72 hours of a valid request from privacy@sproutsong.com. Send written confirmation to the requester.

Anonymised aggregate data (city, board, type counts — no PII) may be retained indefinitely for product analytics.

🛡 Critical security measures
  • Server-side validation — allowlist approach. Use express-validator to validate every field. Reject any field not in the schema using strict: true on Mongoose and .not().exists() for admin-only fields. Never trust frontend validation alone.
  • NoSQL injection prevention. Add express-mongo-sanitize as global middleware before all routes. This strips $ and . operators from all inputs, preventing MongoDB operator injection via email or phone fields.
  • Field-level encryption for PII. Apply mongoose-field-encryption to schoolEmail, schoolPhone, contactPerson, contactEmail, primaryContact, altMobile. Use a 32-byte key from environment variables. Never store plain-text contact data.
  • adminStatus & scheduledAt — reject from client. Use body('adminStatus').not().exists() and body('scheduledAt').not().exists() in the public POST route. Hardcode status: 'draft' on every new submission.
  • notes field — sanitize XSS. This free-text field renders in the admin panel. An attacker can submit a script tag to execute in admin's browser (stored XSS). Escape with .escape() on input. Use DOMPurify in the admin frontend before rendering.
  • schoolLogo URL — no server-side fetching. If the backend ever fetches the submitted logo URL to validate or cache it, an attacker can send an internal IP (e.g. 169.254.169.254) to probe cloud metadata (SSRF). Validate format only — never server-fetch a user-submitted URL.
  • Rate limiting: 5 submissions per IP per hour. Use express-rate-limit backed by Redis. Return HTTP 429 on breach. Prevents automated spam and database flooding.
  • CAPTCHA — reCAPTCHA v3 or Cloudflare Turnstile. Public form with no authentication. Validate the CAPTCHA token server-side before processing any submission.
  • CORS: restrict to auth.sproutsong.com only. No wildcard * origin. Reject all other origins at the API level.
  • Duplicate detection. Index on schoolEmail. If the same email submits within 24 hours, return the same generic success response — do not create a duplicate record and do not reveal the duplicate to the caller.

  • Purpose limitation. Data collected here must only be used for demo scheduling and follow-up. It must not be added to a marketing list, shared with third parties, or used for advertising without explicit separate consent.
  • Right to erasure. Provide privacy@sproutsong.com as the deletion contact. Hard-delete the record within 72 hours of a valid request. Send written confirmation.
  • Retention periods. Draft: 30 days (TTL index). Submitted/active: 12 months after last interaction. Closed: 6 months then purge.
  • PII masking in logs. schoolEmail, contactEmail, primaryContact, altMobile must never appear in plain text in server logs or error messages. Use a log serializer that masks these fields before writing to any log stream.

🛡 Critical security measures
  • File upload security (std8–std12, photoPath) — highest priority. Accept only PDF, JPG, PNG. Validate MIME type server-side — never trust file extension alone. Max 5 MB per file. Rename to UUID on save (e.g. a3f9b2.pdf). Store in private bucket — never public /uploads. Serve via signed URL with 15-minute expiry. Scan for malware before storage (ClamAV or cloud-native scanning).
  • IDOR protection on file access. When a counsellor requests a file (GET /files/:referenceId/:field), verify server-side that the requesting counsellor's assignedCases includes this referenceId. Never serve a file by path or filename alone — always cross-check ownership.
  • Encrypt financial data at rest. fatherIncome and motherIncome are sensitive financial PII. Apply field-level encryption in MongoDB (mongoose-field-encryption or MongoDB CSFLE). Never return these in API responses unless the requester is an authorised counsellor/admin. Never log them.
  • referenceId must be server-generated only. Generate server-side using UUID v4 or nanoid. Use .not().exists() in express-validator. A client-submitted referenceId could overwrite another student's record.
  • isMinor flag — derive from dob, never accept from client. Calculate age server-side. If under 18, set isMinor: true on the document. Enforce parentConsentGiven: true before saving minor records.
  • Cascade delete — DB + files. On erasure request, delete the MongoDB document AND all associated files from the storage bucket. A DB deletion that leaves orphaned files is an incomplete erasure under DPDP.
  • Financial data nulling on case closure. When status transitions to closed/counselled, run a server-side update to null fatherIncome and motherIncome. This is data minimisation in practice.
📜 DPDP Act obligations
Children's data: Students are likely under 18. DPDP Act requires verifiable parental/guardian consent. A simple checkbox is not sufficient — the parent must actively confirm their identity as guardian.
  • Parental consent — mandatory and verifiable. Add a separate parent/guardian consent declaration. Store consent with timestamp, IP, and the parent contact field used. The form must not submit without parentConsentGiven = true when isMinor = true.
  • No negative profiling of the child. DPDP Act restricts processing detrimental to a child's wellbeing. Never store labels like "weak academic", "dropout risk". AI-generated insights must use constructive, supportive language only.
  • No advertising profiling on children's data. interests, preferredCollege, and budget must never be used for targeted advertising. Counselling purpose only.
  • Financial data minimisation. fatherIncome and motherIncome should be nulled on case closure. Document this in your Privacy Policy under "data minimisation".
  • Purpose limitation for documents. Uploaded marksheets must only be used for counselling assessment. They must not be shared with colleges, third parties, or used for any other purpose without explicit separate consent.
  • Right to erasure for guardian. Parent/guardian can request full deletion — DB record + all files. Process within 72 hours. Use referenceId or email as the lookup key.

import multer from 'multer';
import { v4 as uuidv4 } from 'uuid';
import path from 'path';
import { S3Client, PutObjectCommand, GetObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';

const ALLOWED_MIME = ['application/pdf', 'image/jpeg', 'image/png'];
const MAX_SIZE = 5 * 1024 * 1024; // 5 MB

const upload = multer({
  storage: multer.memoryStorage(), // never write to disk
  limits: { fileSize: MAX_SIZE },
  fileFilter: (req, file, cb) => {
    if (!ALLOWED_MIME.includes(file.mimetype))
      return cb(new Error('Invalid file type'), false);
    cb(null, true);
  }
});

// Upload to private S3 bucket
async function uploadToPrivate(file, studentId, fieldName) {
  const ext = path.extname(file.originalname).toLowerCase();
  const key = `counselling/${studentId}/${fieldName}/${uuidv4()}${ext}`;
  await s3.send(new PutObjectCommand({
    Bucket: process.env.PRIVATE_BUCKET,
    Key: key,
    Body: file.buffer,
    ContentType: file.mimetype,
    ServerSideEncryption: 'AES256',
  }));
  return key; // Store only the key in MongoDB — never a public URL
}

router.get('/files/:referenceId/:field', authMiddleware, async (req, res) => {

  const url = await getSignedUrl(s3, new GetObjectCommand({
    Bucket: process.env.PRIVATE_BUCKET, Key: key
  }), { expiresIn: 900 });
  res.json({ url });
});

🛡 Security measures
  • Duplicate booking prevention. Index on email + preferred_date. If same email submits for same date within 24 hours, return the same generic success response without creating a duplicate. Prevents both accidental duplicates and calendar flooding.
  • CAPTCHA — mandatory. Public form, no authentication. Without CAPTCHA, bots can mass-register fake workshops and flood the scheduling system. Use reCAPTCHA v3 or Cloudflare Turnstile, validated server-side.
  • status and submittedAt — hardcoded on server. Reject these fields from the client payload. An attacker sending status: "confirmed" must not be able to auto-confirm their own registration. Use .not().exists() in validation.

  • Email confirmation must not leak. The confirmation email sent to the registrant should contain only their own data. Never include counts of other registrants, other school names, or booking slot availability.
  • Rate limiting: 3 submissions per IP per day. Workshops are low-frequency events. 3/day is generous for a legitimate user and blocks automation.
📜 DPDP obligations
  • Consent checkbox (adult standard consent). Add an unchecked-by-default checkbox: "I consent to SproutSong collecting my name, email, and phone to schedule and confirm the AI workshop and for follow-up communication." Store consentGiven, consentTimestamp, consentIP.

  • Right to erasure. Registrant can request deletion before or after the workshop. Process within 72 hours. After a completed workshop, null PII fields but retain anonymised record for 12 months.
  • No secondary use of contact data. Name and email from this form must not be added to a CRM or marketing list without explicit opt-in. Workshop registration ≠ marketing consent.

Full secure route with honeypot + TTL schema
import { body, validationResult } from 'express-validator';
import rateLimit from 'express-rate-limit';
import mongoSanitize from 'express-mongo-sanitize';

// Rate limiter
const contactLimiter = rateLimit({
  windowMs: 60 * 60 * 1000,
  max: 5,
  message: { message: 'Too many submissions. Please try again later.' },
});

// Validation
const contactValidation = [
  body('name').trim().isLength({ min: 2, max: 100 }).escape(),
  body('email').isEmail().normalizeEmail().trim(),
  body('phone').optional().matches(/^[6-9]\d{9}$/),
  body('message').trim().isLength({ min: 10, max: 2000 }).escape(),
  body('status').not().exists(),      // server-set only
  body('submittedAt').not().exists(), // server-set only
  body('website').not().exists(),     // honeypot
];

router.post('/contact', contactLimiter, mongoSanitize(), contactValidation, async (req, res) => {
  // Honeypot — silent reject (same response as success)
  if (req.body.website)
    return res.status(200).json({ message: 'Your message has been received.' });

  const errors = validationResult(req);
  if (!errors.isEmpty())
    return res.status(422).json({ message: 'Please check your submission.' });

  await new ContactRequest({
    name:        req.body.name,
    email:       req.body.email,
    phone:       req.body.phone || null,
    message:     req.body.message,
    status:      'pending',       // hardcoded
    submittedAt: new Date(),      // hardcoded
    resolvedAt:  null,
  }).save();

  // Log without PII
  console.log(`Contact form received — ip: ${req.ip}, ts: ${new Date().toISOString()}`);

  // Generic response — no record ID returned
  res.status(200).json({ message: 'Your message has been received. We will respond within 2 business days.' });
});

// ——— Mongoose schema with TTL index ———
const contactSchema = new Schema({
  name:        { type: String, required: true, trim: true, maxlength: 100 },
  email:       { type: String, required: true, trim: true, lowercase: true },
  phone:       { type: String, default: null },
  message:     { type: String, required: true, maxlength: 2000 },
  status:      { type: String, enum: ['pending','resolved','closed'], default: 'pending' },
  submittedAt: { type: Date, default: Date.now },
  resolvedAt:  { type: Date, default: null },
}, { strict: true });

// Auto-delete 6 months after resolution
contactSchema.index(
  { resolvedAt: 1 },
  { expireAfterSeconds: 15552000,  // 180 days
    partialFilterExpression: { resolvedAt: { $ne: null } }
  }
);
